## テスト作成基準

- **全画面・全コンポーネントにテストを書く。** 「目視確認」は補助であり、テストの代替にならない
- 新規ファイルごとに対応する `.test.ts[x]` を作成する。テストなしの production コードは REVIEW で 🔴
- 動作が変化する全 UI 要素（ボタン、フィルタ、フォーム、ダイアログ、disabled 制御）をテストする
- seed データとの共存: ページネーション付き API のテストで全件 `find()` しない。フィルタで絞る（[TSTD-4](../../../04_standards/02_testing.md#TSTD-4)）
- **Test ID 規約（tdd-audit が実行証跡で照合する）**:
  - **ID は `TEST-<sprint_id>-<major>.<minor>` の形で書く**（例: `TEST-17-11-1.1`）。`<sprint_id>` は
    `.sprint/flags.json` の active。`<major>` / `<minor>` はスプリント内で 1 から振ってよい。
    前置により ID が全スプリントで一意になり、長命なテストファイル上での衝突が起きない。
    `spec-lint` ゲート（test-id）が形式を強制する（[GATE-4](../../../06_process/gate-tools.md#GATE-4)）
  - テスト定義行（表の先頭セルが Test ID の行）には**テストファイル列が必須**
  - テストファイル列に「同上」を書かない。行ごとにパスを書く。`tdd-audit` は行内から直接パスを読むため、「同上」は空欄として FORMAT fail になる
  - テストの**実行名**（`describe` と `it`/`test` の連結名）に Test ID を含めること。`it()` 名に直接書くのが基本形（`describe('TEST-<sprint_id>-x.y ...')` で囲む形でも可）。**コメント内の ID は照合されない**
  - テストの名前には、そのテストが検証する振る舞いを定める条項の ID を `[[ID]]` の形で Test ID と並記する（[TSTD-6](../../../04_standards/02_testing.md#TSTD-6)）
  - 実テストを持たない検証項目（行数確認・集合確認・手動確認等）には **Test ID を振らない**。「静的検証項目」の表に種別と方法を書き、qa が TEST ステージで実測する（[TSTD-1](../../../04_standards/02_testing.md#TSTD-1)）

## 静的検証項目

テストを持たない検証。**種別を宣言し、種別に応じた方法を書く**（[TSTD-1](../../../04_standards/02_testing.md#TSTD-1)）。種別と方法が無い項目は REVIEW で 🟡。

| ID | 種別 | 対象 | 方法 | 期待値 / 判定条件 |
|----|------|------|------|------|
| S-1 | 機械走査 | app/src | `command grep -rn 'TODO' app/src` | 0 行 |

- 機械走査: 式・期待値・数える単位（行 / ファイル）・除外を書く。式は `command grep` かスクリプトで実行する
- 構造走査: ツールのコマンドと期待値を書く
- 読み取り: 読む範囲と、不合格になる記述を書く。「同じ規範を述べる行が無いこと」だけでは判定できない
