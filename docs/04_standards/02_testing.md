# テスト方針

テストの規範。条項 3 つ（静的検証の書き方・seed データとの共存・テストの名前に条項 ID を書く）。

---

<a id="TSTD-1"></a>
### [TSTD-1] 1.3 静的検証の書き方

静的検証項目は、テストを持たない検証（残存 0 件・集合の一致・条項本文の正しさ）を TEST.md に書く場所である。**項目ごとに種別を宣言し、種別に応じた方法を書く。** 種別は 3 つに固定する。

| 種別 | 対象 | 機械で取れるか | TEST.md に書くもの |
|------|------|------|------|
| 機械走査 | 識別子・ID・英語キー・パス・記法 | 取れる | 走査式・期待値・数える単位・除外 |
| 構造走査 | 条項の参照・アンカー・表の列・ルート集合 | 取れる（ツール） | ツールのコマンド（`spec-graph.sh reverse <ID>` / `deps` / `clause-anchors.sh --check` / `impl-sync.sh`）と期待値 |
| 読み取り | 自然言語の規範文・図・JSDoc・条項の値の実在 | 取れない | 読む範囲（`sed -n '<開始>,<終了>p' <file>` またはファイル全文）・判定条件（何が書いてあれば不合格か）・読んだ人 |

**「走査」は機械走査と構造走査だけを指す。** 自然言語の規範文を対象にする行為は「読み取り」と呼ぶ。自然言語は表記ゆれ・語順・同義の言い換えがあり、パターンでは取れない。「同じ規範を述べる行を走査した」と書くと、実際には読んでいない範囲が「走査済み」として記録される。読み取りは範囲を機械で切り出し（`sed -n`）、判定だけを人に残す。

**走査式は bash スクリプトか `command grep` で実行する。** 対話シェルの `grep` は Claude Code が ugrep に置き換えたシェル関数であり、`.gitignore` の対象・隠しファイル・バイナリを黙って除外する。同じ式でもスクリプト（`/usr/bin/grep`）と結果が変わる。TEST.md に書く式は、qa がスクリプトとして再実行して同じ値になるものにする。

`grep` で「旧名が 0 件」を主張する機械走査は、次の規則で書く。

#### 走査の対象と語を切り分ける

1. **対象に生成物を入れない。** `**/migrations/**` は適用済みのマイグレーションとスナップショットであり、書き換えないので減らない。走査から必ず除外する
2. **語が層を跨いで同綴りになるときはソースの grep を判定に使わない。** `total_amount` は DB のカラム名として正しく、API のキー名としては誤り、ということが起こりうる。判定は応答の走査（API を叩いてキーを見る）に置き、ソースの grep は内訳の提示に使う

```bash
# 正: 生成物を除外する
grep -rn 'old_field_name' src | grep -v '/migrations/' | grep -v '\.test\.'

# 禁止: 適用済みマイグレーションが数に入る
grep -rn 'old_field_name' src | grep -v '\.test\.'
```

- **走査式は削除対象の形まで限定する。** 同じ識別子が同じファイルの中で 2 つの役割を持つことがある。`grep 'oldKey'` ではなく `grep 'oldKey: source'` のように、削除する行の形を書く
- **走査語は「改名前の綴り集合」から機械的に作る。** 改名前の綴りを全件列挙し、そのすべてを走査語にする。列挙は改名対象の定義（設定のキー一覧・DB の `SELECT DISTINCT key` 等）から取る
- **期待値 0 の走査と分類の走査を、層ごとに漏れなく割り当てる。** 同じ綴りが frontend と backend の両方にあるとき、「どの層をどちらの走査が見るか」を表にして空欄を残さない
- **走査範囲は仕様書のディレクトリ（要件〜詳細仕様）を含める。** プロセス文書・計画文書・決定記録は含めない。過去の実測と撤回の記録が証跡として残るため、期待値 0 に到達しない。そのスプリントが変更対象にするディレクトリは例外として含め、逸脱であることと理由を TEST.md に書く
- **既存テストに残る旧綴りを先に数える。** 過去スプリントのテストには不在アサーションのリテラルが残っている。テストを含めた期待値 0 の走査を置く前に、既存の残存を 0 にできるか確かめる。できないなら、その語では分類の走査を使う
- **残存は分類とセットで示す。** 「何行残ったか」ではなく「何を指す行が残ったか」を書く。同じ語が DB のテーブル名・カラム名・格納値・変数名のどれを指すかで正誤が逆になる

#### 削除の検証は静的走査に一本化する

旧名を消す変更では、削除の検証を静的走査（grep 期待値 0）に置き、テストの不在アサーションに置かない。不在アサーションを書くにはテストに旧綴りのリテラルが要り、同じスプリントの中で「テストが要求する記述」と「走査が禁じる記述」が衝突する。

- **期待値 0 を置いて削除を主張する走査は、テストファイルも対象に含める。** 分類して内訳を示す走査はテストファイルを除外してよい。除外するときは、その走査が分類用であることを検証項目に明記する
- **テストに旧綴りを書かない。** 書く必要が出たら、その不在アサーションを落とす
- **文字列を分割して走査を避けない。** `['total','cost'].join('_')` のような書き方は禁止する
- テストが担うのは新しい綴りが動くことである。旧綴りが消えたことは走査が担う

例外は **API の入力値**である。`?sort=created_at` が 400 になることのように、外部から旧値を渡せる経路は、旧値を拒むことをテストでアサートする。この場合の旧綴りはテストの入力データであり、走査の対象語を実装側の識別子に限る。例外に当たるときも、旧綴りは URL やクエリ文字列の中にだけ書く。`{ sort: '<旧名>' }` のようなキーと値の組の形で書かない。

#### 条項の規範語を書き換えるときは 3 種を読む

条項の規範語を変えるとき、指摘された行だけを直さない。同じ規範を述べる別の場所が残る。範囲を次の 3 種に固定し、見つけた箇所を全件タスクに載せる。b の ID 参照だけが構造走査で、残りは読み取りである。

| # | 種別 | 範囲 | 見るもの |
|---|------|------|---------|
| a | 読み取り | 当該条項を含むファイルの全文 | 同じ規範を別の語で述べる行（表・注・制約一覧） |
| b | 構造走査 + 読み取り | `bash harness/tools/spec-graph.sh reverse <ID>` が返す参照元と、設計文書の全文 | 条項を引く記述と、ID を引かずに同じ規範を書く記述 |
| c | 読み取り | SPEC の禁止事項・README の OUT OF SCOPE・完了基準 | 旧規範を前提にしたスコープ記述 |

読み取りの項目には、読む範囲と「不合格になる記述」を書く。「同じ規範を述べる行が無いこと」だけでは判定できない。

#### 図と JSDoc は走査に掛からない

grep は mermaid フェンス・ASCII レイアウト図・JSDoc の中の規範を拾えない。**UI 画面仕様のような図を多く含む文書を是正するスプリントは、読み取りの静的検証項目を 1 件以上置く。** 項目には読む範囲（`sed -n '<開始>,<終了>p' <file>`）と、図が是正後の条項と矛盾しない条件を書く。

#### 走査が自分の説明対象を巻き込むときは書き方の側を決める

記法・語彙そのものを変えるスプリントでは、走査式が説明のために書かれた例示を数えてしまう。**走査式に除外を足して対症療法にしない。** 記法の例示はコードフェンス内に書くと決め（[RULE-1](../05_specifications/README.md#RULE-1)）、走査式は「フェンス内を除外する」だけを持つ。

#### 外部レンダラへの依存は SPEC に書く

自分が制御しないレンダラ（GitHub・Obsidian 等）の挙動を前提にする仕様は、その前提を SPEC に書く。前提を書けば、外れたときにやり直す範囲が決まる。例: アンカーの形は「GitHub が `<a id>` を残し、フラグメントを解決する」ことを前提にしている。

<a id="TSTD-2"></a>
### [TSTD-2] 1.4 識別子を書く条項は実在まで突合する

条項が**外にある名前**（テーブル名・カラム名・関数名・型名・環境変数名）を書くとき、静的検証を「その値が**書かれているか**」で終わらせない。**その名前が実装に実在するか**まで検査項目に書く。種別は読み取り（条項の値を人が取り出す）+ 機械走査（取り出した値を実装で引く）である。

| 検査の種類 | 通る例 | 見逃すもの |
|---|---|---|
| 存在確認 | 「条項すべてが入力型・担当サービスを書いている」 | 書いてある値そのものが実装と違うこと |
| 内容突合 | 「条項が書く識別子が実装に実在する」 | — |

書式の検査は書式の誤りしか見つけない。存在しない識別子・分岐の欠落は、条項を実装と突合して初めて出る。

## 8. テストデータ

<a id="TSTD-4"></a>
### [TSTD-4] 8.1 seed データとの共存

テストは seed データが存在する DB 上で実行される。以下を守ること:

- **ページネーション付き API のテストで `find()` を使って特定レコードを全件から探さない。** seed データの件数でページ境界が変わり、テストが flaky になる。代わりに API のフィルタパラメータ（`id` 等）で対象を絞り込む。実害: フィルタなし応答への `find()` が、データの増加によりページ外へ押し出されて失敗する事例がある
- **順序の検証と特定レコードの取得を分ける。** ソート順（タイブレーカー含む）の検証はフィルタなしリクエストで維持してよい。ただしその応答から特定レコードを `find()` で探さない
- **件数アサーション（`toHaveLength(N)`）は、フィルタで対象を限定した上で使う。** フィルタなしの全件カウントは seed データ量に依存する
- **テスト用レコードのコードや名前には一意プレフィックス（例: `TEST-`）を付ける。** seed データとの衝突を避ける

## 3. テストの配置

テストファイルは対象ファイルと同一ディレクトリに `{name}.test.ts` で配置。`__tests__/` ディレクトリは作らない。

<a id="TSTD-6"></a>
### [TSTD-6] 3.1 テストの名前に条項 ID を書く

テストの名前（`describe` / `it` / `test` の第 1 引数）に、そのテストが検証する振る舞いを定める条項の ID を `[[ID]]` の形で書く。テストの名前は仕様とテストを結ぶ記録であり、`bash harness/tools/spec-graph.sh reverse <ID>` がそのテストを `path:line` で返す。

- **コメントには書かない。** コメントは実行証跡に載らず、`spec-graph` も読まない
- **実装コードには書かない。** 実装と仕様の結び付きは名前の照合（`impl-sync`・frontmatter の `impl`）に任せる
- **Test ID（`TEST-<sprint>-x.y`）と並記する。** Test ID は `tdd-audit` の照合対象、条項 ID は `spec-graph` の照合対象で、役割が違う
- 置く位置: ファイルの全テストが同じ条項を検証するなら最上位の `describe` の名前に 1 つ。条項が分かれるなら、分かれる `describe` か `it` の名前に置く。1 つの名前に複数の `[[ID]]` を書いてよい
- 書く条項は次の順で探す。(1) テストの対象ファイルを frontmatter の `impl` に持つ仕様文書の条項。(2) その文書が無いテスト（gate ツール・hook・スクリプト）は `docs/06_process` / `docs/04_standards` の条項。画面共通や UI 部品の汎用の条項は、(1) の文書に該当する条項が無い振る舞いにだけ使う。決めるときは今の条項本文を読む。スプリント文書は読まない
- ID は `bash harness/tools/spec-graph.sh index` の nodes に実在する条項を指す。`bash harness/bin/sprint spec-graph`（V3）が検証する。テストファイルの走査範囲と、テストの名前の行の定義はゲート仕様（`docs/06_process/gate-tools.md` の graph の節）にある
