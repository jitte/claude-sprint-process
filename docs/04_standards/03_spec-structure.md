# 仕様の構造

仕様の集合に構造を上流で当てはめ、後からリファクタリングするための規範。条項 4 つ（構造・雛形で当てはめる・リファクタリングの型と完了条件・手順）。

---

## 1. なぜ構造が要るか

仕様は 1 本ずつ書かれ、互いに参照し、後から増える。構造が無いと、同じ規範が複数の場所に書かれ、どれが正本か分からなくなり、参照先の節番号が動いても気づけない。構造があれば、規範は 1 箇所にあり、参照は機械が辿り、変更は参照元に伝わる。

構造は、最初の仕様を書く時点で当てはめる。書き終えた仕様に後から当てはめると、参照の付け替えと正本の判定に大きな作業が要る。当てはめる手段は雛形である。雛形に書けば、書いたものが検証できる形になる。

スプリントの成果物は、その時点の基準で正しい。基準を後から上げたとき、既存の仕様との間に差が出るのは、仕様が壊れたからではなく、基準が変わったからである。リファクタリングは、今ある仕様を実態として、規範を変えずに構造と内容の評価を上げる操作である。同じ構造を目指すので、別の規範ではない。

規範の内容（`the system shall` / `If 〜 then` の数と意味）は、当てはめる作業でもリファクタリングでも変えない。規範文の追加・削除・意味の変更は、これらと 1 つのスプリントに混ぜない。

<a id="SSTD-1"></a>
### [SSTD-1] 1.1 構造

仕様の層構造は設計から導く。

| 設計が決めるもの | 仕様の側に現れる形 |
|---|---|
| ドメインの分割（どの業務がどの集約を持つか） | 業務モジュールの層。上位仕様 1 本と末端の仕様 N 本 |
| 共通の振る舞い（書き込み口・エラーの形・時刻・ページネーション） | 横断の共通仕様。全層が参照する |
| 画面の共通 UX（骨格・部品・入口） | 画面の層。上位仕様 1 本と画面の仕様 N 本 |
| API 規約（パスの形・応答の形） | 各モジュールの API の節が従う条項 |

層ごとに上位仕様が 1 本あり、末端の仕様はその特化である。末端は上位との差分だけを書く。上位に書かれた規範は再記述せず、`[ID](<相対パス>#ID)` で参照して従う。

構造を守るのは次の 4 原則である。

| # | 原則 | 守る機械 |
|---|---|---|
| 1 | 一つの規範は一箇所にだけ書く。他所は参照する | 無い。人が読んで見つける |
| 2 | 参照は機械が辿れる形で書く。切れたら検出する | V3 / V8 / V9 / V11 |
| 3 | 参照先が変わったら参照元に知らせる | `spec-graph.sh diff`（条項の内容ハッシュ） |
| 4 | 参照グラフは DAG である。循環は検出する | V10 |

4 原則から導かれる扱い。記法は [RULE-1](../05_specifications/README.md#RULE-1) に置く。

- **参照の向きは指標であり、制約ではない。** 層・階層・フォルダを参照の可否に使わない。向きの集計は `spec-graph.sh layers` が出す
- **頂点は 1 個とは限らない。** 1 つの仕様が複数の観点から導かれるのは普通である。導出元は参照そのもので表す。親を宣言しない
- **条項を持つ文書は `xref-prefix` の宣言で決まる。** フォルダは置き場である
- **参照は「この規範に従う」の宣言である。** 所在の案内・下流の説明・参考文献の紹介にはリンクを付けない。表題を平文で書く
- **上位と食い違うことを末端に書かない。** 上位を直す。食い違いを末端に置くと、同じ事柄の所属が二重になる

<a id="SSTD-2"></a>
## [SSTD-2] 2. 雛形で当てはめる

新しい仕様ファイルは雛形から作る。雛形は `harness/templates/` に 2 つあり、取り込み時に `docs.templates` へ写す。

| 雛形 | 使う場面 | 持つ形 |
|---|---|---|
| `spec-upper.md` | 層を新しく起こすとき | 3 節。①その層に共通する規範 ②その層の構成 ③下位仕様が書く差分 |
| `spec-leaf.md` | 層の中にモジュール・画面を足すとき | 冒頭に「差分の範囲は上位の条項に従う」の 1 行。以下は固有の責務・規範・API または画面の振る舞い・テスト観点 |

**上位仕様は索引ではなく要約である。** 3 節のどれが欠けても「上位を読めば層の全体が分かる」が成り立たない。

1. **共通する規範** — 全下位に適用される契約。下位はこれを再記述せず参照する
2. **構成** — 何が下にあり、それぞれ何を担うか。1 行ずつ。相互に排他で、全体を覆う
3. **下位が書き足す差分** — 下位が上位に対して何を書き足し、何を書かないか。表で書く

**末端の仕様は差分だけを書く。** 冒頭の 1 行で、自層の「下位が書き足す差分」の条項に従うことを宣言する。上位の規範に条件を足すときは、上位を参照したうえで追加条件だけを書く。

雛形に書いた形は、次の検査の対象になる。

| 雛形の行 | 検査するもの |
|---|---|
| `[ID](<相対パス>#ID)` の参照 | 実在（V3 / V8 / V9）・循環（V10）・内容の変化（`diff`） |
| 冒頭の「差分の範囲は … に従う」 | 単独率（`spec-coverage`。`docs.normativeDirs` / `docs.commonFiles` に上位仕様を入れたとき、上位を 1 つも参照しない末端を数える） |
| frontmatter の `xref-prefix` | V1 / V6 |
| 条項の見出し `[ID]` とアンカー | V2 / V9。`clause-anchors.sh` が設置する |

## 3. 対象の選び方

指標の定義とコマンドは `docs/06_process/spec-metrics.md` に置く。指標の定義は `/spec-coverage` スキルにも置く。本節は、構造の評価と内容の評価が低い場所を見つけるときの見方だけを書く。

| 見るもの | コマンド | 読み方 | リファクタリングの型 |
|---|---|---|---|
| 節番号・略称での参照 | `bash harness/bin/sprint spec-graph`（V11） | 参照先の節番号が動いても検出されない参照 | A |
| 循環 | 同上（V10） | 規範の辺と案内の辺が混ざっている | F |
| 被参照 0 の条項 | `bash harness/bin/sprint spec-coverage --unreferenced` | 参照元が無い規範。規範でないものが条項になっている場合を含む | E |
| 条項の外にある行が多い（cov が低い） | `bash harness/bin/sprint spec-coverage` | 条項化されていない規範か、説明文か。本文を読んで決める | G |
| 単独率が高い | 同上（`docs.normativeDirs` があるとき） | 末端が上位を引かず、自前で書いている | C / H |
| 層の向きが期待と逆 | `bash harness/tools/spec-graph.sh layers` | 参照の誤りではなく、規範の置き場所を疑う | D |
| 1 ファイルの被参照が偏って多い・行数が多い | `bash harness/tools/spec-graph.sh files` | 読者が違う節が 1 ファイルにある | B |
| `resolve` の出力が大きい | `bash harness/tools/spec-graph.sh resolve <FILE>` | 到達する条項に読み物が混ざっている。案内をリンクで書いている | F |
| 表題の重複 | 走査。見出しから条項 ID・節番号・括弧を除いた表題を取り、2 ファイル以上に現れるものを数える。コードフェンスの中は除く | テンプレートの節名・同名で別内容・参照済み・内容の重複の 4 つに分ける。操作の対象は内容の重複だけ | C / H |

- **値に閾値を置かない。** 値は対象を選ぶための材料であり、合否ではない
- **同名は重複の証拠ではない。** テーブル定義と API 契約、設計判断と振る舞いは、同じ表題で別の役割を持つ。本文を読んで振り分ける

<a id="SSTD-3"></a>
## [SSTD-3] 4. リファクタリングの型と完了条件

リファクタリングは 8 つの型に分ける。完了条件は機械で出す値で書き、期待値は基準点（`<base>` = 作業開始時の commit）に対して PLAN で試走して得る。

| 型 | 操作 | 変えないもの | 完了条件 |
|---|---|---|---|
| A 節番号参照の条項化 | 参照先の節に条項 ID を付け、参照を `[ID](<相対パス>#ID)` に書き換える。参照の前後の語は残す | 条項の本文 | `spec-graph verify` OK。`diff <base>` の changed が 0、added が ID を付けた節と一致 |
| B 読者で分割 | 1 ファイルを、読者（そのエージェントが 1 タスクで読む集合）ごとに分ける。条項の本文は移すだけ。`xref-prefix` は分割先ごとに決める | 条項の本文 | `diff <base>` の changed が 0、removed が 0。旧パスへの参照が生きている文書に 0 件 |
| C 写しを参照にする | 正本を決め、写しを「〜に従う」の 1 文にする。写しにだけある差分は残す。ID の無い正本には先に ID を付ける | 各参照元が到達する規範 | `verify` OK。`diff <base>` の changed が判定表の条項と一致。`resolve <写しのファイル>` で正本の本文が 1 回だけ出る |
| D 規範の移動 | 条項を、内容に合う文書へ移す。ID は変えない。prefix が変わるときは新 ID を付け、`reverse <旧 ID>` の参照元を全件付け替える | 条項の本文 | `verify` OK。旧 ID が生きている文書とテストに 0 件 |
| E 棚卸し | 被参照 0 の条項を 1 件ずつ、消す・参照元を書く・条項の宣言を外す（規範でないもの）のどれかにする | 参照される条項 | `--unreferenced` の一覧が判定表と一致 |
| F 循環の解消 | 循環の辺のうち案内の辺を、平文の表題に書き換える。規範の辺は残す | 規範の辺 | `verify` OK（V10 が 0 件）。外した参照を README に記録する |
| G 昇格 | 表・説明文を条項にする。値を実装と突合してから写す（[RULE-1](../05_specifications/README.md#RULE-1)） | — | `verify` OK。`diff <base>` の added が判定表と一致 |
| H 共通化 | 2 つ以上の条項が同じことを言う部分を上位の条項に抜き出し、各条項から参照する。各条項に固有の部分は残す | 各参照元が到達する規範 | `verify` OK。作業前後で、各参照元の `resolve` が到達する規範文の集合が同じ |

C と H は、規範文の数を変えてよい（H は 2 文が共通 1 文と参照 2 本になる）。守る不変条件は数ではなく、各参照元が到達する規範の集合である。差分を消して 1 つに揃える判断は共通化ではなく規範の変更であり、仕様変更として ADR と SPEC の「決定」に理由を残す。

正本の決め方（型 C / H）。次の順で決める。

1. 規範文（EARS）を持つ文書
2. 被参照が多い文書
3. 文書の役割（設計 = 判断と構成、仕様 = 振る舞い、参考 = 原理と採用方針）

判定の問いは「この文を消したら、参照元の規範が成り立たなくなるか」である。成り立たなくなる文が規範で、正本は 1 箇所である。

守ること。

- **一括置換をしない。** 候補を抽出し、1 件ずつ本文を読んで直す。同じ綴りが 2 つの意味を持つ（DB の列名と API のキー名）。一括置換は規模に比例して誤りを増やす
- **封印済みのスプリント文書を書き換えない。** 過去の SPEC に残るリンク切れは受け入れる
- **参照を足すと循環になる箇所は、「従う」の宣言を平文の表題で書く。** リンクにしない
- **条項を新設しても、前の条項は `diff` の changed に出ない。** 出たら本文を変えている

<a id="SSTD-4"></a>
## [SSTD-4] 5. 手順

1. 基準点を記録する。`<base>` = 作業開始時の commit
2. 対象集合を走査で全数出す。issue の「約 N 件」は目安であり、対象集合ではない。走査式は TEST.md に置く
3. 判定表を作る。列は「対象 / 型 / 正本 / 扱い / 理由」。変えないものにも理由を書く
4. 進め方を決める
   - 判断を伴う（正本を選ぶ・条項化する・消す・共通化する）: スプリント（kind=docs）。判定表を SPEC.md に持ち、qa が REVIEW で全行の本文を実測する
   - 判断を伴わず、規範もツールも変えない（型 A / B / D の機械的な部分）: スプリントを起こさない。active スプリントが CLOSED の状態で行い、PR にする
5. 完了条件の検査を、作業前の木で試走する。期待値をその出力から取る
6. 1 件ずつ実行する
7. 出口で次を実測する
   - `bash harness/bin/sprint spec-graph` が OK
   - `bash harness/tools/spec-graph.sh diff <base>` の changed / added / removed が判定表と一致する
   - 参照元ごとに `bash harness/tools/spec-graph.sh resolve <FILE>` が到達する規範文の集合が作業前と同じである（C / H は集合で、他の型は規範文の数でも同じ）
   - 手順 2 の走査を再実行し、対象集合が 0 件か判定表と一致する
   - `bash harness/tools/clause-anchors.sh --check` が 0 件
8. 判定表と実測値を SPEC.md / TEST.md に残す。恒久化する規則は `docs/06_process/sprint-process.md` の「RETRO と恒久化の手順」節に従う
