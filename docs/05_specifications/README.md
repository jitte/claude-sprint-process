# 05 詳細仕様

EARS 形式で記述するモジュール仕様の書き方規範。条項 ID・参照記法・`api-routes` 宣言を定める。

---

### frontmatter

```yaml
---
xref-prefix: FOO
layer: core
impl: src/domain/foo/
---
```

| 項目 | 必須 | 意味 |
|------|------|------|
| `xref-prefix` | 必須 | 条項 ID の接頭辞。英大文字 2〜6 字。コーパス全体で一意。**これを宣言した md が条項を持つ。** フォルダは関係ない |
| `layer` | 任意 | 指標。書くなら `common` / `core` / `supporting` / `generic` / `operation` / `frontend` / `design` のいずれか。`bash harness/tools/spec-graph.sh layers` の集計に使う。参照の可否を決めない |
| `impl` | 任意 | 主実装パス（リポジトリ相対）。書いた場合は実在が検証される |

## [RULE-1] 3. 条項 ID と参照

### 条項の宣言

見出しまたは表行の先頭セルに `[CORE-4]` の形で埋め込む。**見出しの直前の行に明示アンカーを置く。**

```markdown
<a id="CORE-4"></a>
### [CORE-4] 3.1 貸借一致検証
```

- 宣言として扱うのは**見出し行または表行の先頭セル**にある `[ID]` だけ。散文中の `[CORE-4]` は宣言でも参照でもない
- **アンカーは見出しの直前の行に単独で置く。見出し行そのものは変えない。** GitHub が見出しから自動生成する id は見出しの本文が混ざるため、文言を直すたびに参照が切れる
- アンカーの設置は `bash harness/tools/clause-anchors.sh` が行う（冪等。手で書かない）
- ID はコーパス全体で重複しない。**連番は追記のみで、欠番を再利用しない**
- 条項の範囲は、次の条項宣言または同レベル以上の見出しまで（下位見出しは範囲に含まれる）

### 何を条項にするか

**条項は「参照されうる規範の単位」である。** 見出しレベルで機械的に決めない。

| 条項にする（規範を持つ） | 条項にしない（非規範） |
|---|---|
| 振る舞い・制約（`the system shall` / `If 〜 then`） | 理由・背景（`なぜ必要か`） |
| 構造定義（テーブル・型・リクエスト/レスポンス形状） | トレーサビリティの列挙（`対応`） |
| 境界の宣言（責務・スコープ・他モジュールとの境界） | 下位を束ねるだけのグルーピング見出し |
| 分類・対応の定義（許可値の一覧・体系） | 図だけの節（mermaid / ASCII 図のみ） |
| 検証観点（`テスト観点` の各節） | 概念の言い換え |

- **判定は節ごとに本文を読んで行う。** 見出し名だけで振り分けない。同名でも片方に規範文があり片方に無いことがある
- **同名の条項を量産しない。** `責務` のように全モジュールに現れる見出しを一律に条項化すると、参照されない条項が増えてグラフが意味を失う。条項名にはモジュール名を入れて一意にする
- **表を条項へ昇格させるときは、セルの内容を実装と突合してから写す。** 表の記述は緩い注記だが、条項は規範になる。昇格は移設ではなく新しい規範を書く作業である。「等」を外して `the system shall` にした値が実装に無い事故が起きる

### 参照

```markdown
別ファイルの条項:   時刻の扱いは [COM-20](10_common.md#COM-20) に従う。
同じファイルの条項: 貸借一致は [CORE-4](#CORE-4) に従う。

二重括弧の記法（docs/07_plans の封印済み SPEC に残る。読み取りは続ける。文書では新しく書かない）:
                    時刻の扱いは [[COM-20]] に従う。

表示文字列に表題を入れる形は使わない:
                    [CORE-4 貸借一致検証](#CORE-4)

他ファイルの節を略称と節番号で指す形は使わない:
                    設計文書 §2 / 仕様書 §4.9
```

- **読み取りで**参照として扱うのは `[<ID>](<相対パス>#<ID>)` / `[<ID>](#<ID>)` と、二重括弧の記法に一致する文字列だけ。`<ID>` は英大文字 2〜6 字 + `-` + 数字
- **相対パスは参照元ファイルからの相対で書く。同じファイルの条項には相対パスを書かない**
- **表示文字列は条項 ID だけにする。** 条項の表題を入れると、表題を変えるたびに全参照の追随が要る
- 参照先の見出しの直前には `<a id="<ID>"></a>` がある。GitHub と Obsidian はこれで実体へ飛ぶ
- **新しく書く仕様・SPEC はリンク記法（`[<ID>](<相対パス>#<ID>)`）だけを使う。** REVIEW ゲート（`harness/gate-tools/spec-lint.sh` の refs）はスプリント SPEC の §0 について**リンク記法しか受理しない**
- **読み取りは二重括弧の記法を受理し続ける。** `docs/07_plans` の封印済み SPEC が使っており、書き換えない。`spec-graph.sh` は両方を参照として解析する
- **テストの名前（`describe` / `it` / `test` の第 1 引数）は参照元である。** テストの名前に書いた条項 ID は `spec-graph.sh` が参照として読む（[TSTD-6](../04_standards/02_testing.md#TSTD-6)）
- **テストの名前では二重括弧の記法を使う。** コードの中でリンク記法は意味を持たない
- 変換は `bash harness/tools/clause-anchors.sh` が行う（冪等）
- コードフェンス内・インラインコード内は走査しない。**記法そのものを例示するときはコードフェンスに入れる**
- **他ファイルの節を略称と節番号で指さない**（上のフェンスの「設計文書 §x」の形。V11 が検出する）。参照先の節に条項 ID を付けて `[ID](<相対パス>#ID)` で書く。同一ファイル内の節番号は書いてよい
- **参照は「この規範に従う」を意味する。** 下流でどう見えるかの説明は参照にしない
- **参照先の内容を再記述しない。** 例外は引用であることを明示した抜粋。参照を足したら本文の再記述を消す。本文を残すなら、それが要約であり規範は参照先にあることを条項に書く
- **新しい層に条項を書くときは、同じ事柄を定めた既存条項を先に引く。** 対象の語で `docs/05_specifications/**` を走査し、当たった条項を読む。重なるなら参照して従う。違うことを書くなら、なぜ違うかを ADR / SPEC の「決定」の表に残す。`spec-graph` は参照の実在と循環を見るが、同じ事柄を別の場所で定めていることは見ない
- **参照を足すときは参照先を読む。** その条項が `the system shall` を持ち、その事柄を定めているかを確かめる。`spec-graph` は参照先の実在は見るが、何を定めているかは見ない

### 層（指標）

参照の向きは依存構造の**評価指標**であり、制約ではない。機械は向きを検査しない。
`layer` を宣言したファイル間の参照を `bash harness/tools/spec-graph.sh layers` が「参照元の layer × 参照先の layer」で数えて表にする。
`layer` の無いファイルは `-` として数える。

```bash
bash harness/tools/spec-graph.sh layers        # 層 × 層の参照数の表
bash harness/tools/spec-graph.sh deps <FILE>   # そのファイルが参照する条項の内訳
```

依存の向きの期待（例: 支援 → コア → 汎用。汎用は読み出しのみ）はプロジェクトの設計文書に書く。集計にこれと逆の向きが現れたら、参照の誤りではなく規範の置き場所を疑う。
層をまたいで共通する規範は共通層（`common`）へ、層内で共通する規範は上位仕様へ移す。

- `xref-prefix` を宣言しないファイル（消費者）は全条項を参照できる。参照はエッジに数えない
- 参照の向きに関係なく、循環は V10 が検出する（思想: 参照グラフは DAG である）

### 検証

```bash
bash harness/bin/sprint spec-graph                          # verify（V1〜V3 / V5 / V6 / V8〜V11）
bash harness/tools/spec-graph.sh files         # 条項を持つファイルの一覧
bash harness/tools/spec-graph.sh layers        # 層 × 層の参照数
bash harness/tools/spec-graph.sh reverse <ID>  # 参照元の逆引き（影響範囲）
bash harness/tools/spec-graph.sh deps <FILE>   # そのファイルが参照する条項
bash harness/tools/spec-graph.sh resolve <FILE># 原文 + 到達する条項の本文
bash harness/tools/spec-graph.sh diff <ref>    # 内容の変わった条項と、その参照元
bash harness/tools/clause-anchors.sh --check   # アンカーと参照リンクの未設置を列挙（書き込まない）
bash harness/tools/clause-anchors.sh           # アンカーの設置と参照のリンク化を適用（冪等）
```

`clause-anchors.sh` は検証ではなく是正のツールである。条項を追加したら実行する。

| # | 検証 |
|---|------|
| V1 | prefix の一意性 |
| V2 | 条項 ID の一意性 |
| V3 | 参照の実在 |
| V5 | `impl` パスの実在 |
| V6 | frontmatter（`xref-prefix` の実在と形式・`layer` の値。条項の見出しを持つのに `xref-prefix` が無いファイル） |
| V8 | リンクの相対パスの実在 |
| V9 | 参照先のアンカーの実在 |
| V10 | 条項参照グラフに循環が無い（自己参照を含む。消費者からの参照はエッジにしない） |
| V11 | 節番号の文字列参照が無い。第 1 パターン: ファイル名の後 8 文字以内に § が来る行。第 2 パターン: 識別子の形の語（`_` か `-` でつないだ語・2 字以上の大文字の語・2 桁以上の数字）または設定 `docs.docAliases` の別名の直後に § と数字が来る行（略称での参照）。コードフェンスの中は対象外 |

V8 / V9 は `docs/06_process/templates/**` を対象から外す。テンプレートの相対パスはコピー先の深さで書くため、テンプレート自身の位置では解決しない。

V11 の対象は生きている文書（テンプレートを含む）・未封印のスプリント SPEC・リポジトリ直下の md である。
普通の語の直後の節番号と、同一ファイル内の節番号（ファイル名も略称も伴わない形。「（§3）」「本書 §6」）は対象外。他ファイルの節を指すときは、その節の見出しに条項 ID を付けて参照する。ファイル名から推測できない略称は `docs.docAliases` に登録する。
テンプレートの節は条項を持たないので表題で書く（例: テンプレート README の「6. RETRO」節）。

REVIEW ゲートで実行する。仕様は `docs/06_process/gate-tools.md` の graph の節に置く。

### API ルートの書き方と `api-routes` 宣言

`bash harness/bin/sprint api-routes` が、実装の公開ルート集合と本ディレクトリが書くルート集合を双方向に比較する。差があれば TEST ゲートが fail する。仕様は `docs/06_process/gate-tools.md` の routes の節に置く。

**ルートは `<METHOD> <path>` の形で書く。** `/api/v1` は付けても省いてもよい。コードブロック・見出し・EARS 文中・使用 API 表のどこに書いてもよい。抽出は次を除く。

| 除外 | 理由 |
|------|------|
| ` ```mermaid ` フェンス内 | 図の participant 名と遷移ラベルは API の定義ではない |
| ` ```api-routes ` フェンス内 | 宣言であって定義ではない |
| `*` を含むパス | `GET /items/*` のような総称表記は単一のルートを指さない |

**パスを略記しない。** `PATCH /deactivate` のような末尾だけの表記は、実在しないルートとして検出される。`PATCH /api/v1/{resource}/:id/deactivate` と完全形で書く。実装に無いルートを説明で挙げるときは `<METHOD> <path>` の形を使わない。

比較のための宣言は ` ```api-routes ` フェンスに書く。**規定元の条項の中に置く。** 宣言と根拠が離れると片方だけ更新される。1 行 1 宣言で、語彙は 2 つだけである。

```
expand <placeholder> = <値>, <値>, ...
alias  <METHOD> <実装のパス> -> <仕様のパス>
```

- `expand` は総称表記を実体化する
- `alias` は互換ルートを正規のパスへ写像する
- 空振りする宣言は fail する（使われないプレースホルダ・実在しない実装パス）
- **未実装・未記述を許容する語彙は持たない。** 乖離は宣言で通さず、仕様か実装のどちらかを直す

**宣言を実装側（コード・コメント・設定）に置かない。** 理由は 2 つある。

1. **実装が自分で自分の検査を免除できてしまう。** 検査の対象が検査の条件を書く構造になり、検査が意味をなさなくなる
2. **実装言語を限定しないため。** 本ディレクトリは実装から独立した契約である。別の言語・別のフレームワークで再実装しても宣言はそのまま使える。実装に依存するのは公開ルートを取り出す手順だけであり、それは差し替えればよい

読み取り範囲は本ディレクトリ配下に限る。実装側に書かれた宣言は読まれず、検査に影響しない。
